Root Cause: HTTP 429 Rate Limiting from routing.openstreetmap.de/routed-bike
What changed between the successful run and the failing run
Commit 72b2949 (Aug 11) introduced the osrmBaseForProfile() function in osrm-route-provider.ts. Before that commit, the cycling planner used:

router.project-osrm.org/route/v1/bike/...

After that commit, it uses:

routing.openstreetmap.de/routed-bike/route/v1/bike/...

The code comment explains the intent: the demo server ignores the profile path segment and gives car-biased results for all profiles; the OSM Deutschland server runs genuine per-profile instances. The switch was correct in principle — but the OSM Deutschland server aggressively rate-limits concurrent requests.

What actually happens when the user clicks "Find Routes"
The provider fires 40 parallel OSRM requests simultaneously (8 bearings × 5 configurations).

Live test results — batch fired against routing.openstreetmap.de/routed-bike:

First batch:  10/40 → HTTP 200 (valid routes, 19.09–31.76 km, all within ±60% tolerance)
              29/40 → HTTP 429 Too Many Requests
               1/40 → HTTP 200 but parse error
Second batch:  0/40 → Status 0 (connection refused — IP blocked entirely)

Live test results — same batch against router.project-osrm.org (the original server):

40/40 → Status 0 (also blocked now, from our IP after being hit earlier)

The old server (router.project-osrm.org) had no rate limit on the first run. When the user's browser sent 40 parallel requests, all 40 succeeded and returned routes. That is why they saw 2 valid routes.

Why walking and jogging still work
They also fire 40 parallel requests to routing.openstreetmap.de/routed-foot. Two reasons they survive:

Different sub-server — routed-foot appears to have a higher concurrent request capacity or looser rate limits than routed-bike. The foot server has been in production use for years and carries much more traffic infrastructure. The bike server is less well-resourced.

User's browser IP history — the foot server was being used before the bike server was ever hit. The rate limit counter per IP is separate per sub-domain. By the time the user tried cycling, their IP's quota on routed-bike was fresh — then the first cycling run consumed it, and subsequent runs hit the 429 wall immediately.

Summary
The failure is entirely due to routing.openstreetmap.de/routed-bike enforcing concurrent-request rate limits that the provider's "40 queries all in parallel" strategy violates. The switch from the demo server to the per-profile OSM Deutschland server (commit 72b2949, line ~72 of osrm-route-provider.ts) was architecturally correct but introduced a rate-limiting failure mode that the code has no handling for. The fix must address one or both of: (a) how many requests are fired concurrently, or (b) what server is used for the bike profile.
