TASK #10 — NEXUS PUB CRAWL PLANNER V1 🍺

We are now moving from the Activity System into the first real Planner Engine.

The goal is to make "Pub Crawl" an actual intelligent planning experience rather than just an activity label.

IMPORTANT:
- This must be completely £0 to build.
- Do NOT add OpenAI.
- Do NOT add Gemini.
- Do NOT add paid APIs.
- Do NOT require API keys.
- Do NOT add Google Maps/Places yet.
- Use deterministic/mock provider data so we can replace it with real providers later.
- Do not break the existing Golden Window or Activity System.
- Preserve the existing premium Nexus visual language.

==================================================
1. ARCHITECTURE
==================================================

Create a modular Planner Engine architecture that works with the existing Activity Registry.

The architecture should support:

Activity
↓
Planner
↓
Requirements
↓
Data Provider
↓
Candidate venues
↓
Scoring
↓
Route optimisation
↓
Generated Plan

Create a new:

lib/planners/

Structure it so future planners can be added without modifying the core planner engine.

For example:

lib/planners/types.ts
lib/planners/registry.ts
lib/planners/pub-crawl-planner.ts
lib/planners/mock-venue-provider.ts
lib/planners/planner-engine.ts

Use strict TypeScript types.

==================================================
3. PUB CRAWL PLANNER
==================================================

Create:

pub-crawl-planner.ts

The planner should accept information such as:

- groupId
- activityId
- goldenWindow
- group location
- preferred duration
- desired number of stops
- budget preference
- walking preference

For V1, sensible defaults are fine.

Example:

4 stops
2–3 hours
moderate walking
medium budget

The planner should:

1. Find candidate pubs from the mock provider.
2. Remove unsuitable candidates.
3. Score candidates.
4. Select the best combination.
5. Determine an optimal order.
6. Calculate approximate walking distance/time using mock data.
7. Generate a complete pub crawl plan.

==================================================
4. MOCK VENUE PROVIDER
==================================================

Create a deterministic mock venue provider.

Do NOT randomly generate data on every request.

Create a realistic dataset of fictional pubs with fields such as:

- id
- name
- latitude
- longitude
- rating
- priceLevel
- openingTime
- closingTime
- atmosphere
- tags
- estimatedWalkingMinutes
- estimatedCost
- capacity
- features

Use fictional venue names.

Make the dataset large enough to demonstrate meaningful ranking.

For example:

The Golden Fox
The Anchor House
The Lantern
The Crown & Compass
The Old Station
The Harbour Arms
The Red Lion
The Copper Tap

These are mock/test venues only.

Make the provider interface replaceable later with a real Places/venue API.

==================================================
5. SCORING ENGINE
==================================================

Create a transparent scoring model.

A venue score can consider:

- rating
- distance
- price
- opening hours
- atmosphere
- group preferences
- walking distance
- suitability for a pub crawl

Do NOT use AI.

The score should be deterministic.

Expose the scoring breakdown so the UI can eventually explain WHY Nexus chose each venue.

For example:

Venue score: 87%

Rating: +18
Distance: +20
Price: +15
Atmosphere: +17
Opening hours: +17

==================================================
6. ROUTE OPTIMISATION
==================================================

For V1, implement a simple deterministic route optimiser.

Given selected pubs:

Start → Pub 1 → Pub 2 → Pub 3 → Pub 4

Choose the order that minimises total walking distance.

Do not over-engineer this.

A simple nearest-neighbour or permutation-based approach is fine for a small number of venues.

The architecture must allow a more sophisticated route provider later.

==================================================
7. GOLDEN WINDOW INTEGRATION
==================================================

The Pub Crawl Planner should use the existing Golden Window.

If a Golden Window exists:

Use its date/time as the preferred planning window.

If no Golden Window exists:

Return a clear planner requirement:

"Create a Golden Window before planning this pub crawl."

Do NOT automatically create one.

The planner should understand the existing match quality:

PERFECT MATCH
STRONG MATCH
PARTIAL MATCH
BEST OPTION

Display that information in the generated plan.

11. PLAN PERSISTENCE

For V1, keep persistence simple.

If the existing database architecture makes persistence straightforward, create a clean plan representation that can later be stored in Supabase.

However:

DO NOT introduce a large database migration unless genuinely necessary.

It is acceptable for V1 to generate the plan client-side and keep it in memory.

The architecture must make future persistence easy.

==================================================
12. ERROR HANDLING
==================================================

Never leave the UI stuck on:

"Planning..."

Every async operation needs:

try/catch/finally.

If the planner cannot produce a result:

Show a useful message.

Examples:

"No Golden Window has been created yet."

"Not enough suitable venues were found."

"No venues fit the selected time."

Do not expose raw technical errors.
