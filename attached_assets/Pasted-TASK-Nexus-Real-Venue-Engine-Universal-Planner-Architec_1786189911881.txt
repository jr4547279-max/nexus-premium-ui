TASK: Nexus Real Venue Engine + Universal Planner Architecture

We are moving Nexus from a prototype planner into a real-world planning engine.

IMPORTANT:
- Do NOT add Gemini or any AI chatbot.
- Do NOT introduce any paid API requirement for this task.
- Do NOT break the existing Golden Window, Activity System, Pub Crawl Planner, group creation, availability, or persistence.
- Before changing anything, inspect the existing architecture and reuse existing abstractions wherever possible.
- Build this incrementally and keep the app compiling after each major change.
- Do not replace working functionality unnecessarily.

CURRENT ARCHITECTURE

Nexus currently has:

Activity Registry
→ Activity selected when creating a group
→ Availability
→ Golden Window Engine
→ Persistent Golden Window
→ Activity-specific Planner
→ Pub Crawl Planner
→ MockVenueProvider

The Pub Crawl Planner already uses a VenueProvider abstraction.

We now need to evolve this into a UNIVERSAL PLANNING SYSTEM where every activity can eventually have its own planner and real venue provider.

==================================================
PHASE 1 — UNIVERSAL PLANNER ARCHITECTURE
==================================================

Inspect the existing files under:

lib/planners/

components/nexus/

Preserve the existing Pub Crawl Planner behaviour.

Create/extend the architecture so planners are activity plugins.

PHASE 2 — REAL VENUE PROVIDER
==================================================

Replace the current mock-only architecture with a provider abstraction that supports real-world venue discovery.

Because we want to keep this zero-cost initially:

Use OpenStreetMap-compatible public data as the first real provider where practical.

Prefer:
- OpenStreetMap / Overpass for venue discovery
- OpenStreetMap coordinates
- existing Nexus location data if already available

Do NOT require a Google Places API key.

Do NOT require a paid service.

Create:

lib/planners/providers/

venue-provider.ts
openstreetmap-venue-provider.ts
mock-venue-provider.ts

The existing MockVenueProvider must remain available for development/testing.

The new provider should implement the existing VenueProvider interface.

It should be capable of discovering relevant real venues based on:

- activity
- latitude
- longitude
- search radius
- category

For example:

Pub Crawl
→ pubs/bars

Restaurant
→ restaurants

Coffee
→ cafes

Bowling
→ bowling alleys

Cinema
→ cinemas

Live Music
→ music venues

Beach
→ beaches

Hiking
→ trails / parks where available

Do NOT pretend that OpenStreetMap provides ratings, prices, booking availability, etc. when it doesn't.

If a field isn't available, represent it as unknown/null rather than inventing data.

==================================================
PHASE 3 — PROVIDER FALLBACK
==================================================

The planner must never crash simply because real venue data isn't available.

Provider strategy:

1. Try the real venue provider.
2. If real data is unavailable or insufficient, gracefully fall back to the mock provider in development/test environments.
3. In production, show a useful empty state explaining that no suitable venues were found.

Expose which provider generated the result so the UI can distinguish:

REAL VENUES
or
DEMO VENUES

Never present fictional venues as real venues.
