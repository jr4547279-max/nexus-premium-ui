NEXUS — JOB 11: PROFESSIONAL RUN ROUTE PLANNER

We now have:
- Real OSRM routing
- OpenStreetMap road/path data
- Genuine route classification (LOOP / OUT_AND_BACK / LINEAR)
- Full route geometry
- Named OSM waypoints
- Golden Window integration
- Live GPS tracking
- Off-route detection
- Leaflet route maps
- Real route data with no fake route claims

DO NOT rebuild or replace any of that.

The goal of this job is to turn the existing jogging planner into a genuinely useful running route planner where the user can control what kind of run they want and compare multiple real routes.

==================================================
3. MULTIPLE REAL ROUTE OPTIONS
==================================================

The planner should return multiple genuine route candidates instead of selecting one route immediately.

Target:
- ideally 3 useful routes
- minimum 1 if only one legitimate route exists

Candidates must come from REAL routing data.

DO NOT fabricate route geometry.

DO NOT invent distances, road names, checkpoints or route types.

Each candidate should contain enough information for the UI to display:

- route geometry
- route type
- distance
- estimated time
- route grade if available
- surface information
- named roads/paths
- waypoints
- start/end
- turnaround if Out & Back
- loop quality if Loop
- data source
- explanation/reason

==================================================
4. ROUTE SELECTION LOGIC
==================================================

Implement proper preference-aware scoring.

The user's selected preferences should influence ranking.

Example:

If user chooses:

5 km + Loop

then genuine loops should rank dramatically higher than Out & Back.

If there is no suitable genuine loop:

DO NOT relabel an Out & Back as a loop.

Instead return:

"No suitable 5 km loop found nearby."

Then optionally show:

"Closest alternative: 4.8 km Out & Back"

If user chooses:

5 km + Either

then rank the best genuine route regardless of type.

If user chooses:

Roads

prefer routes dominated by road/highway segments.

If user chooses:

Paths / trails

prefer footways, paths, parks and suitable trail surfaces.

If user chooses:

Mixed

balance the two.

Difficulty should influence ranking when reliable route information exists.

Do NOT pretend to know elevation if the current routing provider does not provide it.

==================================================
5. DISTANCE TOLERANCE
==================================================

Do not require an exact distance.

Use a sensible tolerance around the target.

For example:

Target 5 km:
ideal approximately 4.5–5.5 km

Target 10 km:
ideal approximately 9–11 km

But make the scoring progressive rather than binary.

A 4.8 km route should score better than a 7 km route for a 5 km request.

Do not return a wildly different route just because it technically exists.

==================================================
6. ROUTE QUALITY SCORING
==================================================

Create a transparent internal scoring model.

Consider:

- distance match
- requested route type
- genuine loop quality
- surface preference
- route simplicity
- route confidence
- route data completeness
- duplicate-route penalty

Do NOT expose meaningless fake percentages.

If you show a score to the user, make sure it represents something understandable.

Examples:

"Best Match"
"Best Loop"
"Flattest"
"Most Direct"
"Best Path Mix"

Only use labels that are actually supported by the route data.

==================================================
7. DEDUPLICATE ROUTES
==================================================

OSRM can return multiple candidates that are essentially the same route.

Detect and remove near-duplicates.

Do not show:

Route 1 = 4.8 km
Route 2 = 4.9 km
Route 3 = 4.8 km

if they follow essentially the same geometry.

Prefer genuinely different route options.

==================================================
10. IMPORTANT: HONEST FAILURE STATES
==================================================

This is critical.

If the user requests:

10 km Loop

and no suitable 10 km loop exists:

DO NOT silently give them an Out & Back.

Show:

"No suitable 10 km loop found nearby."

Then provide alternatives:

"Closest loop: 7.8 km"
"Closest route: 9.6 km Out & Back"

Give the user the choice.

Likewise:

If no route satisfies the surface preference, explain that honestly.

Never fake compatibility.

15. PERFORMANCE
==================================================

OSRM requests are currently parallelised.

Do not create an uncontrolled number of requests.

Set a sensible maximum candidate count.

Deduplicate aggressively.

Cache the route search for the current:

- location
- target distance
- route type
- surface
- difficulty

so changing UI state unnecessarily does not hammer OSRM.
